Services

Plugins build on each other through services: a provider publishes an interface from a package it exports, and a plugin that requires the provider looks the service up. This is how Jasper's own features compose: Remote and File Server take credentials from the Credential Vault, Remote opens remote files in the Editor, Project Index lists projects on Remote's saved hosts, and Shell History saves commands as snippets. A third-party plugin can use those services, or publish its own, the same way. {@link PluginContext#services()} is the plugin's {@link Services}.

Providing a service

Put the interface, and the values it uses, in a package of their own and list it under {@code exports}. Only that exact package is visible to other plugins; a subpackage must be listed too, and everything else in the plugin stays private.

id = "dev.example.notes"
exports = ["dev.example.notes.api"]
package dev.example.notes.api;

import java.util.List;

/** What other plugins may ask of Notes. Call it on the UI thread. */
public interface NotesApi {
    /** @return the titles of the saved notes */
    List<String> titles();
}

Publish during {@code start}, on the UI thread:

List<String> titles = new ArrayList<>(List.of("Runbook", "On-call rota"));
context.services().publish(NotesApi.class, () -> List.copyOf(titles));

{@link Services#publish(Class,Object)} gives every consumer the same instance; {@link Services#publishPerConsumer(Class,Function)} gives each consumer its own, made by a factory that Jasper calls on the UI thread just before that consumer starts, with the consumer's {@link PluginInfo}, so the provider knows who is asking (the Vault's grants are per plugin this way). A factory that returns {@code null} gives that consumer nothing. Jasper refuses a publication outside {@code start}, of a class that is not an interface, of an interface that is not in one of the provider's exported packages, and of an interface another plugin already published. Publications become visible only when {@code start} returns normally, so no consumer sees a service from a plugin that failed to start; they last until Jasper quits, with no withdrawal.

Using a service

A consumer lists the provider under {@code requires} and compiles against its exported package. Its class loader then sees that package, and only while the provider is loaded.

requires = [{ id = "dev.example.notes", version = ">=1.0", optional = true }]
/** Every line that names Notes's classes is in here, so a missing Notes plugin is caught in one place. */
final class NotesStatus {
    static String summary(Services services) {
        try {
            return services.find(NotesApi.class).map(api -> api.titles().size() + " notes").orElse("Notes is not running");
        } catch (NoClassDefFoundError absent) {
            return "Notes is not installed";
        }
    }
}

Look services up in {@code start}: Jasper starts the providers a plugin requires first and prepares its instances before its {@code start}, and {@link Services#find(Class)} and {@link Services#require(Class)} are then cache reads, safe from any thread. {@code find} is empty when no provider the plugin requires offers the interface; {@code require} throws {@link ServiceUnavailableException}. A plugin sees services only from plugins it lists under {@code requires}.

A hard requirement guarantees the provider: the consumer does not load without it. With {@code optional = true} the consumer loads either way, so it must survive the provider's absence. When the provider did not load, its classes do not exist for the consumer, and the first line that names them throws {@code NoClassDefFoundError}, even a lambda that only takes one as a parameter; keep every use of them behind one guard, as above. An optional requirement's {@code version} range is not checked, so a consumer that calls a method added in a later provider version catches {@code NoSuchMethodError} too, as Remote does for newer Editor methods.

Topics between plugins

A provider can also publish events: a plugin publishes on topics whose id starts with its own id and a dot, and any plugin may subscribe. Put the {@link Topic} constant and its payload type in the exported package; the Vault's {@link dev.jasper.vault.api.VaultApi#LOCK_STATE_CHANGED} ({@code dev.jasper.vault.lock-state}) is one.

package dev.example.notes.api;

import dev.jasper.sdk.events.Topic;

/** The topics Notes publishes. */
public final class NotesEvents {
    /** @param count how many notes there are now */
    public record NotesChanged(int count) { }

    /** Published after every change to the notes. */
    public static final Topic<NotesChanged> CHANGED = Topic.of("dev.example.notes.changed", NotesChanged.class);

    private NotesEvents() { }
}
// The provider, from any thread:
context.events().publish(NotesEvents.CHANGED, new NotesEvents.NotesChanged(3));

// A consumer, on the UI thread (behind the same guard when its requirement is optional):
context.events().subscribe(NotesEvents.CHANGED,
    changed -> context.log().log(System.Logger.Level.INFO, changed.count() + " notes"));

Delivery is queued: handlers run later on the UI thread, in one order for the whole application, never during {@link Events#publish(Topic,Object)}. There is no replay, so a late subscriber reads the current state from the service and then listens. One topic id carries one payload type; using it with another throws. Jasper's own topics are {@link AppEvents} ({@code jasper.app.theme-changed} and {@code jasper.app.config-reloaded}), {@link Activities#TOPIC}, {@link Activities#CONNECTIONS} and the {@link TerminalEvents}, which need {@code terminal.observe}.
