Settings

A plugin's settings live in its own TOML file, {@code plugins//.toml} in Jasper home, not in {@code config.toml}. The plugin declares each setting while it starts: its key, kind, default and how Settings shows it. Jasper then reads the file, checks every value against its kind, reports what it rejects, reads the file again whenever it changes, and gives the plugin a page in Settings › Tools under its name. {@link PluginContext#settings()} is the plugin's {@link PluginSettings}.

Declaring

PluginSettings settings = context.settings();
Setting<Integer> parallel = settings.declare(SettingSpec.of("transfers.parallel", SettingKind.integer(1, 16), 4)
    .label("Parallel transfers").description("Files copied at the same time.").section("Transfers"));
Setting<String> target = settings.declare(SettingSpec.of("target", SettingKind.choice(List.of(
        Choice.of("staging", "Staging", "staging"), Choice.of("production", "Production", "production"))), "staging")
    .label("Deploy target").section("Deploys"));
Setting<List<String>> checks = settings.declare(SettingSpec.of("checks", SettingKind.stringList(), List.of("lint", "test"))
    .label("Checks to run").section("Deploys").applies(Applies.RESTART));
parallel.onChanged(value -> context.log().log(System.Logger.Level.INFO, "Parallel transfers: " + value));

The file the user edits, or Settings writes:

target = "production"
checks = ["lint", "test", "smoke"]

[transfers]
parallel = 8

{@link PluginSettings#declare(SettingSpec)} works only on the UI thread while {@code start} runs, and returns a {@link Setting} that already holds the file's value. A declaration needs a {@link SettingSpec#label(String) label}; a key declared twice, or a key inside another declared key, is refused. Keys are dotted: each part is letters, digits, {@code _} and {@code -}, and each dot but the last names a TOML table. Do not change a {@link SettingSpec} after declaring it: Settings reads its section, description, editor hint and unit again whenever it shows the page. Its builder methods are:

{@link SettingSpec#label(String)}The row's name. Required.
{@link SettingSpec#description(String)}A note under the control.

{@link SettingSpec#applies(Applies)}{@link Applies#RESTART} marks the row "Takes effect after restart". It changes only the label: the value and its listeners still change at once, and a plugin that reads the value only in {@code start} picks it up at the next launch.

{@link SettingSpec#unit(String)}A unit after a number, such as {@code min} or {@code MiB}, at most 16 characters.

A text rule is plugin code: one that throws rejects the value. A default the kind rejects throws when the spec is built. Within Jasper a {@code number} setting's value is kept in single precision, so {@code 0.1} reads back as {@code 0.10000000149011612}; round it where that matters.

Reading the file

Jasper checks the file once a second and reads it again when it changed; Reload Config reads every plugin's file again and then publishes {@link AppEvents#CONFIG_RELOADED}. Problems appear with Jasper's other configuration problems, naming the file and, for a value, its line and column:

  • A value its kind rejects is replaced by the setting's default and reported as the table above shows.
  • A key nothing declares is reported as "Unknown setting or table; ignored."
  • A value of the wrong TOML type, such as a string where an integer belongs, rejects the whole file ("Expected type; configuration was not applied."), and so does a TOML syntax error, a file larger than 1 MiB or one that cannot be read ("file could not be read: why; the last good settings stay in force."). Every setting keeps its last good value until the file is fixed.

{@link Setting#get()} is the value in force, safe from any thread. {@link Setting#onChanged(Consumer)} runs on the UI thread when that setting's value changes, whether the file changed or the plugin saved it; {@link PluginSettings#onChanged(Runnable)} runs once after any declared value changed. The runtime closes these registrations when the plugin stops.

When the file is missing, the first launch that finds the plugin creates it: a copy of the {@code settings.toml} at the root of the plugin's jar, or a one-line header, "# Settings for name version (id). Jasper reads this file live." Jasper never overwrites an existing file. Ship a {@code settings.toml} of commented examples so users who open the file see every setting.

Saving

{@link Setting#set(Object)} writes a new value to the file, keeping its comments, and returns a {@code CompletableFuture} that completes on the UI thread once the setting's handle shows the value. It fails with {@code IllegalArgumentException} when the kind rejects the value, with the message {@link SettingKind#check(Object)} gives (for an integer, "Use a whole number from min–max."), and with {@code IllegalStateException} or {@code IOException} when the file changed on disk since it was read ("key changed on disk. Review the new value and try again."), has errors ("file has errors; fix them before saving settings."), would exceed 1 MiB, or the plugin has stopped. It is safe from any thread; the write itself happens off the UI thread.

The plugin's page

A running plugin that declared settings gets a generated page, Settings › Tools › name: one row per setting in declaration order, with its label, control, description and a way to reset it to its default, and a heading wherever the section changes. Apply saves the changed values to the file. A plugin the user meant to run but that is not running (waiting for a review, skipped, failed or held back by safe mode) gets a page that says "Start name to edit its settings.", gives the reason and offers Open in Editor for the file.

A plugin that needs more than rows gives a page of its own with {@link PluginSettings#page(SettingsPanel)}, once, while it starts. Settings calls {@link SettingsPanel#create(SettingsPanelHost)} the first time the page is shown in each opening of Settings; the page returns a view. {@link SettingsPanelHost#row(Setting)} gives the standard row for a declared setting, bound to the page's unsaved value, and Settings saves those on Apply itself. {@link SettingsPanelHost#stage(Setting,Object)} sets an unsaved value from a control of the plugin's own and {@link SettingsPanelHost#changed()} says the page's modified state changed. {@link SettingsPanel#modified()}, {@link SettingsPanel#apply()} and {@link SettingsPanel#reset()} cover only state of the plugin's own beyond its declared settings; {@link SettingsPanel#dispose()} runs when Settings closes the page.
