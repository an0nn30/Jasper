Lifecycle

Jasper loads plugins once per launch, before its first window opens, and stops them when it quits. A plugin's life is two calls on its entry class, {@link Plugin#start(PluginContext)} and {@link Plugin#stop()}, both on the UI thread, with one {@link PluginContext} that attributes everything the plugin does to it.

At launch

  1. Discover. Jasper looks in the application's bundled plugins, in {@code plugins//jars/} in Jasper home, and in the {@code --plugin-dir} folder (its {@code jars/} folder, or the jars directly in it). In Jasper home a plugin's folder must be named after its id. Exactly one of a plugin's jars holds its manifest.
  2. Pick one copy of each id. The higher version wins; on equal versions the {@code --plugin-dir} copy beats an installed one, which beats the bundled one. The copy that loses is ignored.
  3. Admit. The plugin's {@code sdk} range must include this Jasper's SDK, the user must not have disabled it, and an installed plugin must have the user's consent to every capability it declares. In safe mode no installed plugin and no look loads.
  4. Resolve. Plugins in a dependency cycle are skipped, then every plugin whose hard requirement is not loading, and at most one look is chosen.
  5. Load. Each plugin gets its own class loader, dependencies first. Loading refuses a jar with a class in a reserved package ({@code dev.jasper.sdk}, {@code dev.jasper.app}, {@code dev.jasper.terminal}, {@code dev.jasper.buddy}, {@code java}, {@code javax}, {@code jdk}) or in a package a dependency exports, a class file larger than 16 MiB, and a class that refers to an SDK type or member this SDK no longer has ("rebuild it for SDK version"). The entry class must be public, have a public no-argument constructor and implement {@link Plugin}.
  6. Start. Jasper calls each plugin's {@code start} on the UI thread, in load order.

Load order puts every plugin a plugin {@code requires}, hard or optional, before it; otherwise plugins go in alphabetical order of id. A plugin whose hard requirement did not become active is skipped with the reason ("requires id, which failed to start", "was skipped" or "is not running"). What became of each plugin is logged as one line per plugin, shown in Settings › Plugins, and, for a plugin that could not be read, loaded or started, posted in the Plugin problems notification group; see plugins.

start

{@code start} registers the plugin's contributions and returns. It runs on the UI thread, which draws every window, so it must return promptly: Jasper logs any plugin callback on the UI thread that takes more than 100 ms ("Slow plugin callback on the UI thread"). Move slow work, such as reading files or connecting, to {@link PluginContext#background()}. Two things are possible only while {@code start} runs: declaring settings with {@link PluginSettings#declare(SettingSpec)} (and giving a settings page with {@link PluginSettings#page(SettingsPanel)}), and publishing services with {@link Services#publish(Class,Object)} or {@link Services#publishPerConsumer(Class,Function)}. {@code start} is also where to look up the services of the plugins it requires: Jasper prepares them before it calls {@code start}, and {@link Services#find(Class)} returns them.

public final class ToolPlugin implements Plugin {
    @Override public void start(PluginContext context) {
        Setting<Boolean> enabled = context.settings().declare(SettingSpec.of("enabled", SettingKind.bool(), true)
            .label("Show the deploy action").applies(Applies.RESTART));
        context.log().log(System.Logger.Level.INFO, "Tool " + context.plugin().version() + " started");
        if (!enabled.get()) return;
        context.actions().register(ActionSpec.of("dev.example.tool.deploy", "Run Deploy Checks"),
            invoked -> context.background().execute(() -> runChecks(context)));
    }

    private static void runChecks(PluginContext context) {
        // Slow work runs here, off the UI thread.
    }
}

When start fails

When {@code start} throws, or the entry class cannot be created, Jasper rolls the plugin back completely: everything the context handed out goes, not only its registrations. Its actions, menus, toolbar and status items, tool windows, content tabs, split items, restorers and dialogs, palette scopes, file sources, subcommand handlers and event subscriptions are removed; open activities end as failed with "Plugin failed to start" and connections close; its notifications expire; staged services are discarded, so no other plugin ever sees them; its background tasks are interrupted; and the context closes. The plugin is reported as failed with "Name failed to start" (with Disable Plugin and Show more…, which opens the Errors tab at its stack trace), and plugins that require it are skipped. {@code stop} is never called after a failed start.

stop

{@code stop} is called once, when Jasper quits, for each plugin that started, in reverse start order. It runs before Jasper closes what the plugin left open, so it can save state or end connections cleanly; afterwards Jasper removes every registration as it does after a failed start, and activities still open end as failed with "Plugin stopped". It must not block: Jasper cannot abandon a blocked UI thread, and a {@code stop} that does not return ends the process at the exit deadline. See Threading for the shutdown order.

The context

Each plugin gets its own {@link PluginContext}. Its members are the SDK's entry points:

MemberWhat it gives
{@link PluginContext#plugin()}The plugin's {@link PluginInfo}: id, name, normalised version and the capabilities it holds.
{@link PluginContext#log()}Its logger.
{@link PluginContext#dataDirectory()}Its private data folder.
{@link PluginContext#background()}Its executor for slow work.
{@link PluginContext#settings()}Declared settings and the Settings page.
{@link PluginContext#events()}The event bus: Jasper's topics, other plugins' topics and its own.
{@link PluginContext#services()}Services it publishes and those of the plugins it requires.
{@link PluginContext#activities()}Activities and connections shown on Desk Buddy.
{@link PluginContext#notifications()}Its notification groups.
{@link PluginContext#actions()}, {@link PluginContext#menus()}, {@link PluginContext#toolbar()}, {@link PluginContext#statusBar()}, {@link PluginContext#rail()}Commands and where they appear; see Contributions.
{@link PluginContext#panels()}, {@link PluginContext#windows()}Tool windows, dialogs, overlays, popovers, content tabs, split items, restorers and file choosers.
{@link PluginContext#kit()}, {@link PluginContext#appearance()}Its view kit, the current theme's colours, the look Jasper runs with and the saved terminal font.
{@link PluginContext#terminals()}Windows, tabs and panes; see Terminals.
{@link PluginContext#palette()}Command palette scopes; see Palette.
{@link PluginContext#fileSources()}Places in Jasper's file chooser.
{@link PluginContext#commandLine()}Its {@code jasper} subcommands.
{@link PluginContext#platform()}Desktop integration: the editor, the browser and the clipboard.

After a failed start, and after {@code stop}, the context is closed: calls that contribute throw {@code IllegalStateException}, {@link PluginContext#background()} rejects tasks with {@code RejectedExecutionException}, and the handles it issued stop working. Queries and commands on window, tab and pane handles throw {@code IllegalStateException} ("Plugin context is closed: id"), and so do the kit's view methods ("Plugin kit is closed"); sending text, bytes or a paste to a pane does nothing; and {@link Setting#set(Object)} fails with "The plugin has stopped." {@link PluginContext#log()} keeps working, so a background task that outlives the plugin can still say why it ended.

Logging

{@link PluginContext#log()} is a {@code System.Logger} named {@code dev.jasper.plugins.}. Its records go to Jasper's log, {@code jasper--.log} in the {@code logs} folder of Jasper home, beside Jasper's own; records at INFO and above are written. Every failure Jasper contains in the plugin's code is logged there at WARNING as "Plugin id failed in what" with its stack trace. See diagnostics.

Data and settings

{@link PluginContext#dataDirectory()} is {@code plugins//data/} in Jasper home, created when missing. The plugin owns its contents. It survives updates and disabling, and is deleted, with the plugin's jars and settings file, when the user removes an installed plugin. The settings file beside it, {@code plugins//.toml}, belongs to declared settings; read and write it through them rather than as a file.

Safe mode and --plugin-dir

{@code jasper --safe-mode} starts Jasper without any plugin installed in Jasper home and without any look; bundled plugins that provide no look, and a {@code --plugin-dir} plugin, still load. {@code jasper --plugin-dir } loads the plugin in that folder beside the others, without a capability review. Use it to run the plugin you are building; see the command line. One Jasper runs per Jasper home: {@code --plugin-dir}, {@code --safe-mode} and {@code --config} apply only to a Jasper that starts, which is then never resident, and a launch while Jasper runs hands its request to that Jasper, which ignores the options and says to quit it first. The Jasper that owns the home serves {@code daemon/commands}, so {@code jasper} in any shell reaches it, and each Jasper that starts updates the subcommand list {@code jasper --help} prints.
