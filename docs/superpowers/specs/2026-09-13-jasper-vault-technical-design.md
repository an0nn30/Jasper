Read the [product contract](2026-09-13-jasper-vault-product-design.md), [core plan](../plans/2026-09-13-moray-vault-core.md), and companion device-access and manager plans together. ## Ownership and dependencies

Everything belongs in `moray-app`, package `dev.moray.app.vault`; no new module, plugin framework or terminal dependency is introduced. One `VaultService` is owned by the application and shared by every window. UI draft fields are separate from committed core data. Public snapshots contain metadata only. Explicit Save invokes a transaction; failed validation, encryption or disk replacement leaves both the previous file and the committed model intact.

Reuse TermLab's Argon2id parameters, GCM primitive, best-effort array disposal and lock/persistence test scenarios. Do not copy its IntelliJ service/UI integration, mutable exposed model, cached master password, device-bound KDF, JSON secret strings, fresh salt on every save, path-based keys or unbounded file reads. These behaviors conflict with the approved Moray contract. Apache MINA SSHD 2.18.0 and Bouncy Castle 1.85.2 are pinned; `bcpkix-jdk18on:1.85` (and its `bcutil-jdk18on:1.85`) accompanies `bcprov-jdk18on:1.85.2` for PEM decoding; the 1.85.2 patch exists only for bcprov, not those companion artifacts. `sshd-common` suffices for import; `sshd-core:2.18.0` is reserved for the SSH deliverable. No connection is opened by this plan.

## Encrypted file

Version 1 is a Moray-only binary format, not a TermLab migration format. It has a fixed 72-byte big-endian header: magic `MORAYVLT` (8), version (4), UUID (16), Argon2 memory KiB (4), iterations (4), parallelism (4), random salt (16), random GCM nonce (12), and ciphertext length including tag (4). The complete header is GCM associated data. Version 1 accepts exactly Argon2id v1.3, memory 65,536 KiB, 3 iterations, 4 lanes, 32-byte output; hostile headers cannot request arbitrary memory or CPU. AES-256-GCM uses a 128-bit tag and fresh random 96-bit nonce for every save. A random 128-bit salt and vault UUID remain stable for the life of this vault, allowing remembered storage of the derived key. Password change/rekey and recovery/export are outside this deliverable.

The payload uses length-prefixed binary values and a payload version. It contains validated settings, separate login records and private-key records. Metadata is UTF-8, decoded strictly. Passwords/passphrases are length-prefixed UTF-16 code units in arrays (no secret `String` serialization). Imported key bytes are encrypted in the vault with their passphrase. The payload limits are 10,000 total entries, 1 MiB per imported key, 4,096 secret characters, 4,096 UTF-8 bytes per metadata string and 16 MiB total file. Negative counts/lengths, oversized input, unsupported versions, duplicate IDs/fingerprints, dangling references, invalid settings, trailing bytes and invalid metadata all fail before publishing state. Tag failure says “Password incorrect or vault authentication failed”; corrupted ciphertext cannot reliably be distinguished from a wrong password.

Use a private same-directory unique temporary file, write/force fully, validate the encrypted result through the decoder, then replace atomically. Creation uses atomic hard-link publication so it cannot replace an existing file even under a race; a filesystem lacking that operation fails clearly. Updates compare the current encrypted file's SHA-256 against the last committed version under an interprocess file lock before atomic replacement. A changed/deleted/replaced file fails with a conflict; no silent lost update. No non-atomic fallback is allowed. Temporary files are cleaned on all paths. POSIX files use 0600, newly created vault directories 0700; Windows files receive an owner-only ACL before any secret-bearing write. Failure to establish private permissions aborts. This promises intact previous-or-new content during a process failure, not a universal guarantee against hardware loss or directory metadata loss.

## Imported keys

`inspectKey` parses an in-memory byte stream with MINA, allowing Ed25519, RSA (at least 2,048 bits), and ECDSA nistp256/384/521. Exactly one private key is accepted. OpenSSH private-key format and PEM formats supported by MINA/BC (including encrypted PEM and PKCS#8 PEM) are supported; public-only, DSA, multiple-key bundles, wrong passphrases, malformed and oversized files fail with a sanitized error. No plaintext temporary file is used. MINA's passphrase callback requires a transient Java `String`; acknowledge that unavoidable library-boundary copy rather than claiming perfect heap erasure.

Fingerprinting is SHA-256 over the SSH public-key blob, displayed in OpenSSH `SHA256:` form. Store its authorized-key public text, type and fingerprint with a stable UUID. Duplicate import returns the existing ID with `duplicate=true` and never silently renames it. The manager previews the fingerprint before committing. Source bytes are copied into the vault; removing the original fixture after import cannot affect credential resolution. Logins reference key UUIDs. Renaming preserves UUIDs. Deleting a referenced key fails; the manager first edits/deletes referencing logins. Host references are absent in this deliverable; the SSH plan must add its real host reference check before enabling deletion of credentials used by hosts.

## Locking, threading and cancellation

The service starts locked and never consults a native credential store in its constructor or `snapshot`. A single UI-owned worker serializes expensive actions. Service state has an independent short monitor and generation counter so `lock` clears secret data and invalidates pending results immediately, even during Argon2/parsing. Slow operations perform work outside this monitor and check their captured generation at a short commit boundary before publication. The operation mutex serializes disk operations, while filesystem and native I/O never hold the state monitor. An encrypted write that crossed that boundary before Lock may finish atomically, but completion rechecks generation and cannot restore unlocked data. A late create updates only public file existence/header/hash; a late save updates only the encrypted-file hash/revision. Candidates and copied keys are cleared when rejected. The worker returns only metadata to the EDT; the UI also checks its operation generation before displaying completion, and closes stale credential material.

`lock(AUTO)` clears live key/model and preserves remembered access; `lock(EXPLICIT)` clears live state first, then persists a revocation marker and removes native remembered data. Already-detached credential material is owned by its caller; locking blocks subsequent resolutions but does not reach into established SSH sessions. Credential material implements `AutoCloseable`; caller arrays are wiped when closed and access after close fails. There is no global active-connection registry.

`userActivity()` is called only for real user input in any Moray window. `checkInactivity()` compares an injected monotonic `LongSupplier` to the last input/unlock time; terminal output, search workers and refreshes never call it. Settings default to 15 minutes, with 0 disabling automatic locking; changes take effect against the existing last-activity timestamp. The core owns no AWT listener or scheduled thread. The manager integration supplies an application-wide event filter and a lightweight timer. The default monotonic source is `System.nanoTime`; wall-clock changes affect only remembered expiration, never inactivity. The four-argument constructor injects both clocks for deterministic tests.

## Remembered device access

`DeviceAccessStore` is the only interface and has multiple real OS implementations in the companion plan: `available()`, nullable `byte[] read(String vaultId) throws IOException`, `write(String vaultId, byte[] payload) throws IOException`, `delete(String vaultId) throws IOException`. The key is a canonical UUID string. The adapter treats payload bytes as opaque, enforces a 2,560-byte limit and never falls back to a normal settings file. `available()` reports adapter capability without reading native secrets.

The core's fixed 64-byte remembered payload is magic/version (8), vault UUID (16), expiration epoch milliseconds (8), and 32-byte unlock key. Enrollment derives a deadline once from the successful master-password unlock plus requested duration (default seven days, configurable 1–365 days). Remembered unlock never renews it. Both the UUID and exact expiration must match the current nonsecret sidecar; deadline equality with `Clock.instant()` is expired. The native payload is independently validated before decrypting the vault. Missing/expired/malformed/mismatched material is unusable and falls back to a password prompt; native access failures remain actionable errors, never “missing.”

A small private sidecar stores UUID, deadline and revocation state, but no key/password. It allows the unlock screen to render the deadline without reading a native secret at startup. It is not an authentication authority: the native payload and vault GCM authentication must both succeed. Missing/malformed/revoked sidecars deny remembered unlock. Enrollment writes native payload first then atomically publishes the matching sidecar; failure attempts native rollback and reports the error. Disabling remembered access in settings performs the same revocation path as explicit lock but can retain the unlocked model. Explicit lock also sets an independent in-process deny latch before waiting on native work; reading a stale sidecar cannot clear it. Only successful password-based enrollment clears that latch. Explicit lock writes the revoked sidecar before native deletion; deletion failure retains the deny marker and reports a warning. If both sidecar persistence and native deletion fail, the in-process vault is still sealed, but restart revocation cannot be guaranteed; the UI must report that exact limitation. No code may present this outcome as a successful deletion.

## Public contract and testing

The core plan contains the exact public types and signatures used by the manager. `VaultSnapshot` includes metadata lists, settings, remembered deadline, revision and a sanitized native-warning string. Locked snapshots have empty credential lists. All mutation APIs persist before returning; there is no second uncommitted core model or separate “save everything” operation. Optional `Duration rememberFor` on password create/unlock is null to leave existing enrollment unchanged; no enrollment is silently created. Settings store only default durations; the optional remember choice belongs to the unlock UI.

Core tests use temporary directories, generated synthetic keys, an in-memory `DeviceAccessStore` and a mutable clock. They cover authentication/header damage, bounded parser rejection, save rollback/external conflict, imported ownership/duplicates/references, non-sliding expiry, startup no native reads, auto/explicit lock distinctions, sidecar tampering, native failure, and stale async unlock publication. Native store acceptance, real desktop windows, actual SSH connectivity and host associations belong to their respective deliverables; none may be claimed from headless core tests.
